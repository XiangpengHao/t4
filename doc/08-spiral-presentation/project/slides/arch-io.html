Start with the right half only: a single thread manages every I/O in the process. It submits reads to io_uring and polls the completion queue, the same two rings as on the io_uring slide. Build 1: each read request reaches that thread through a message-passing channel (an mpsc channel, src/io/io_worker.rs). Build 2: the callers can be on any runtime, tokio, smol or a plain thread; t4 assumes no executor. Build 3: a completion wakes the caller's task. Default queue depth is 64. Off Linux, the same interface runs on a thread pool, and tests run on a simulated drive (src/io/mod.rs).

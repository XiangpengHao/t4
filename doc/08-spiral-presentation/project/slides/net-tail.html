Reading from the network is extremely noisy. The same kind of request, sorted from fastest to slowest, spans an order of magnitude: with 1,024 GETs in flight straight from S3, median 451 ms, p99 3,686 ms, slowest 7,281 ms (doc/05-network.md). At 256 in flight it was 175, 407 and 861 ms. A query's GETs run in parallel and the query ends only after the slowest one finishes, so the max is what matters, not the median. A real case from run 6 on 26 Oct: one 23 s GET turned a 3.5 s query into a 26 s run. The left chart is drawn to the same scale as the bars on the right: seven GETs around the 451 ms median (35 to 56 px for 380 to 600 ms, illustrative) and one at the 7,281 ms slowest, which is where the query ends. You also wanted a chart of one request type's latencies sorted from lowest to highest: the per-GET CSV (store.gets.csv from run_queries) has what it needs.

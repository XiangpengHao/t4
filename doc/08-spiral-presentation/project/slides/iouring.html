Keep this gentle. io_uring is relatively new: Linux 5.1, 2019. The app and the kernel share two ring buffers. 1: the thread writes read requests into the submission queue, many at once, with no system call per read. 2: the kernel picks them up. 3: with O_DIRECT the SSD writes by DMA straight into your buffer: no page cache, no copy. 4: the kernel posts a completion. 5: the thread reaps completions. Compare with the pread slide: no copy, and one system call can cover many reads. tokio's file reads can't do this: tokio::fs runs a blocking pread on its thread pool. Vortex's local reader, FileReadAt, also preads on a blocking pool; vortex-duckdb chose it over tokio's pool, which it calls very bad for local reads on high-core machines (doc/09-vortex-integration.md).

Why shared mode: Python's global interpreter lock means a Python application scales out with processes, not threads: multiprocessing pools, data-loader workers, one process per core. Each process links t4, so each has a t4 of its own. If each built its own cache, each would hold its own memory tier, fetch the same blocks again, and fight over the same cache files. Instead, a cache built with T4CachingBuilder::with_multiprocess_sharing takes an exclusive lock on its cache files. The first t4 to get it owns the cache: the index, the memory tier, the policy and the disk tier, served from a thread of its own (doc/11-shared-mode.md, decision 1). Every other t4 finds the files locked and becomes a client of the owner: requests and answers cross a Unix socket, and the bytes come through a shared memory region the owner maps, with no copy. A client fetches the blocks the cache doesn't hold itself, with its own credentials, and the owner keeps them for everyone. If the owner's process exits, its clients read from the remote until one of their reads makes a t4 the next owner. None of this reaches the application: it calls t4 the same way whichever role its t4 has. In Spiral today, Studio and spiral connect share one cache this way (doc/10, decision 8); check what the Python client turns on before saying it ships with it.

Caching policies are pluggable

One trait decides where every block lives. The cache keeps no access state of its own: the policy hears every hit.

trait PlacementPolicy {

// fetched from S3: memory, disk, or nowhere?

fn on_remote_read(&self, read) -> Admit;

// read from disk: stay, or move up to memory?

fn on_disk_hit(&self, chunk, read) -> DiskHit;

fn on_memory_hit(&self, chunk, read);

fn on_admit(&self, tier, chunk, block);

// a tier is full: which chunks give way?

fn pick_memory_victims(&self, n) -> Vec<MemoryVictim>;

fn pick_disk_victims(&self, n) -> Vec<ChunkId>;

}

Default

CLOCK per tier

Fetched blocks go to memory. Memory’s victims move down to disk. A disk block read twice moves back up.

For benchmarks

FixedPlacementPolicy

Every fetched block goes to one tier, or none, so a run measures memory hits alone or disk hits alone. Vortex’s bench uses it too.

Where a block lives is a trait, PlacementPolicy (src/cache/policy/mod.rs), one policy for both tiers. Every hook takes &self, so a policy keeps whatever state it wants with whatever concurrency it wants; the cache keeps none. Each hook on the read path gets the block, the file's size and path, and the range the read asked for. on_remote_read is asked as the read plans its fetches, so the policy hears of every remote read, even the ones it doesn't cache. on_disk_hit is asked before the read, so a move up reads the block straight into a memory chunk, one I/O. The default is a lock-free CLOCK per tier (clock.rs). FixedPlacementPolicy (fixed_placement.rs) admits every fetched block where one setting says, memory, disk or nowhere, and never moves a disk hit up: t4's bench uses it, and so does Vortex's (doc/09-vortex-integration.md, decision 7). How a read is served is a second trait, ReadPolicy, whose default is the p90 racing from earlier in this part.

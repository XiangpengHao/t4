Part 2: t4 against Kismet, the cache Spiral runs on a user's machine today. Kismet keeps every 1 MiB block as a file of its own: Spiral sizes it in files, its 20 GiB default divided by the 1 MiB block, so about 20,000 files, in 64 shard folders (doc/10). Every block read is file-system work: open the file by path, fstat it, read its header and then its payload through the page cache, check a CRC32 over the whole block, close (spiral-kismet-cache, read_envelope). Every write makes a temp file, writes it in five calls, then sets its time and makes it read-only and renames it into place (kismet-cache raw_cache::insert_or_update). Eviction lists a shard folder and stats every file in it. t4 has one cache file per drive, allocated when the cache starts; a block is an offset in it, found in the in-memory bbtree, and read or written with one O_DIRECT request through io_uring, the read landing in the buffer the caller gets.

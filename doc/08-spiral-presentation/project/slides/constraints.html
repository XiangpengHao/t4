Design goals of t4

Direct I/O by default

Disk reads and writes skip the page cache: O_DIRECT into page-aligned memory. The SSD’s DMA is the only copy.

Minimal CPU overhead

No CPU copies and no system call per read: one io_uring thread drives every SSD. The cores stay with the query.

Any async runtime

t4 runs under tokio or any other executor. It owns one I/O thread and assumes no runtime. You pass in a timer.

TLS as it is

Remote reads use standard TLS. No home-made encryption in its place to save CPU.

The goals t4 is built around, and most papers don't hold themselves to. One: direct I/O by default. t4 opens its cache files with O_DIRECT (src/cache/cache_files.rs), so every disk read and write skips the page cache and the SSD writes straight into page-aligned memory; T4CachingBuilder::with_direct_io(false) turns it off. Two: minimal CPU overhead. The pread slides' costs are gone: no CPU copy, and one io_uring_enter per batch instead of a system call and an interrupt per read; for remote reads, S3's rate on the fewest cores. Three: it must be runtime agnostic. You can't say tokio is not supported. t4 keeps one I/O thread of its own and never assumes an executor; a late race needs a timer, which the user gives with T4CachingBuilder::with_sleep (doc/06-read-modes.md, decision 7). Four: you can't invent your own encryption and replace TLS to win a benchmark.

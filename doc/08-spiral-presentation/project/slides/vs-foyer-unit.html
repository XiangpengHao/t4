Part 1: t4 against foyer, the Rust hybrid cache RisingWave, SlateDB and Chroma use. Why the unit matters: a Vortex file is columnar, and a query reads only the columns it needs, plus the footer that says where they are. ClickBench's table has 105 columns, and its queries read a handful. t4 caches a file as 1 MiB blocks, so it caches exactly the blocks the query read: the hot columns' blocks and the footer, and the cold columns never leave the remote. foyer caches a whole value per key: a load returns the key and the whole value, decoded with the app's Code implementation. Keyed by file, the value is the whole file, every column, for a query that read two. And on disk a foyer entry has to fit in one block, 16 MiB by default less a 4 KiB index; a larger value is dropped, only a metric counting it (foyer-storage engine/block/flusher.rs, buffer.rs), so a whole Vortex file of any size stays memory only. An app could split each file into keyed ranges itself, but then it is building a block cache on top of foyer: choosing the ranges, and stitching reads that cross them. The diagram is a schematic.
